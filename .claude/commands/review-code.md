description: 実装コードをプロジェクト規約・アーキテクチャに照らしてレビューし、承認後に自動修正する
---

# コードレビュー (review-code)

引数: レビュー対象のパス（ファイルまたはディレクトリ）

```
/review-code src/app/services/debate_orchestrator.py   # 単一ファイル
/review-code src/app/services/                          # ディレクトリ
/review-code src/app/static/app.js                      # フロントエンド
```

---

## ステップ1: 対象コードの確認

1. 引数のパスが存在するか確認する（ファイルまたはディレクトリ）。
2. ディレクトリの場合は対象ファイル一覧を把握する。
3. パスに `static/` が含まれる場合はフロントエンドと判定し、評価観点を調整する。

## ステップ2: コードレビュー（サブエージェント起動）

`implementation-validator` サブエージェントを起動してレビューを実行する:

- subagent_type: "implementation-validator"
- description: "Code review against project guidelines"
- prompt:
  ```
  以下のコードをレビューしてください。

  ## 対象コード
  [対象ファイルのパスと内容]

  ## 参照ドキュメント
  以下のドキュメントを読んで、プロジェクトの規約・アーキテクチャを把握してください:
  - `docs/development-guidelines.md` — コーディング規約・フロントエンドガイドライン
  - `docs/architecture.md` — アーキテクチャ制約・レイヤー構造
  - `docs/repository-structure.md` — ファイル配置規則

  ## 評価観点

  ### バックエンド（Pythonコード）
  1. **コーディング規約** — `docs/development-guidelines.md` の命名規則・型アノテーション・エラーハンドリング基準
  2. **アーキテクチャ整合性** — レイヤー境界（routers→services→infra）・依存方向の違反がないか
  3. **既存パターンとの整合性** — コードベース内の類似実装（`src/app/services/`等）との一貫性
  4. **セキュリティ** — 入力バリデーション・カスタム例外（`LLMError`等）の適切な使用
  5. **テスト可能性** — DI・モック可能な構造になっているか

  ### フロントエンド（JS/CSS/HTMLコード、パスに `static/` が含まれる場合）
  1. **コーディング規約** — `docs/development-guidelines.md` のフロントエンドガイドライン準拠
  2. **XSS対策** — ユーザー入力・外部データを `escHtml` でエスケープしてから `innerHTML` に挿入しているか
  3. **CSS注入対策** — CSSクラス名にホワイトリスト検証を使用しているか
  4. **インラインスクリプト・スタイル禁止** — `<style>` タグや `<script>` インラインブロックがないか
  5. **Vanilla JS原則** — 外部フレームワーク（React・Vue等）を使用していないか

  ## 出力形式

  問題がある場合:
  - 問題の説明、ファイルパスと行番号、現状のコード、なぜ問題か、修正案

  問題がない場合:
  - 「コードレビュー完了 - 問題なし」と明記し、総合評価スコア（1-5）を記載
  ```

## ステップ3: 結果報告と修正の実施

### 問題がない場合

「コードレビュー完了 - 問題なし」とユーザーに報告して終了。

### 問題がある場合

1. 問題箇所・理由・修正案をユーザーに列挙して報告する:

```markdown
# コードレビュー結果

## 対象: [ファイル/ディレクトリパス]

### 問題点

1. [問題の説明] (優先度: 高/中/低)
   - ファイル: [パス:行番号]
   - 現状: `[現在のコード]`
   - 問題: [なぜ問題か]
   - 修正案: `[推奨するコード]`

### 総合評価

[1-5]/5

### 次のアクション

- [修正対応1]
- [修正対応2]
```

2. ユーザーの承認を得てから `Edit` ツールで各ファイルを修正する。
3. 修正完了後、変更内容のサマリーをユーザーに報告する。

---

## 注意事項

- `/review-docs [path]` がドキュメントの**品質レビュー**（修正なし）を行うのに対し、このコマンドは**実装コードのレビューと修正**を目的とする。
- コードの修正はユーザーの承認後にのみ実施する。
- レビューは詳細な分析のため、数分かかる場合があります。
